# 需求：首条软件生产闭环

状态：首版完整闭环需求；当前 `0.1.0a5` 已有执行/成果适配、知识采用、反馈与明确学习候选投递。真实候选验收、后续本地应用与发布，以及已测的恢复/取消窗口均有各自记录，不能相互代替；既有试点的只读组合恢复已验证，真实副本切换和完整生产资格仍待验证。当前实现范围见[公共接口](INTERFACE.md)，现场与历史状态见[开发记录](DEVELOPMENT.md)。

## 目标与使用者

使用者是推进软件任务的人，以及代表其发起任务的 CLI、应用或 Agent。当前执行和成果保存已有基础组件，但调用方仍需要自行串联目标、请求、查询、失败处理、成果版本和验收记录。

本组件把这些步骤组织成可恢复、可追溯的生产过程。它属于生产方向的控制组件；现有可选 K 适配器提供知识读取、准确版本采用和使用反馈，Owner 已批准接通明确学习候选的可靠投递。首版不以完整知识平台、插件市场或全部规划仓库先建成为前提。

长期目标是通过明确契约组合可替换的执行、验证和基础能力。首版只实现一个具体软件流程，不能据此宣称所有执行器、部署位置或领域已经可替换。

## 首版场景

调用方有一项真实的单文件修改任务，已明确目标和验收条件，并能提供修改后的文件内容。所选 Local Hand 部署已经登记对应项目来源和固定验证能力。

控制组件保留目标及输入，提交任务，在任务副本中取得修改和验证结果。失败时保留原尝试，并在获准范围和预算内接收修订方案；成功封存后归档候选成果。审查者通过指定成果版本取回原内容，核对实际修改和验证结果，给出验收决定。

这条流程的交付物是候选成果及其验收记录。原项目是否更新必须另有应用结果，不能从任务副本里的成功推断。

## 当前需求

| 编号 | 需要的行为 | 可观察的成功标准 |
| --- | --- | --- |
| R1 | 明确目标与输入 | 每次运行能定位原目标、验收条件、来源、输入内容及所选能力；后续修复保留原要求 |
| R2 | 受控执行 | 准备、提交和查询绑定同一 Local Hand 任务身份；准备本身不算业务执行 |
| R3 | 收集真实结果 | 原始执行观察、验证输出和可取得的证据可定位；失败、未知、证据缺失分别呈现 |
| R4 | 修复后继续 | 调用方可在原范围内提交修订输入；旧失败不被覆盖，已完成业务不会以“恢复”为名重跑 |
| R5 | 取消和重启接续 | 取消请求与退出证明分开；控制进程重启后查询原任务，不创建替代任务猜测结果 |
| R6 | 保存和使用准确版本 | 合格候选归档后保存明确 Artifact/Version 引用；审查实际使用读回内容，并记录使用版本及结论 |
| R7 | 根据原目标验收 | 验收决定关联目标版本、候选版本、证据及作出决定的主体；测试通过不自动代替验收 |
| R8 | 独立使用 | 在独立环境安装后，通过本仓公开入口使用；不导入上层应用私有模块，不依赖理论仓或维护对话运行 |
| R9 | 保留生产与学习的双向边界 | 能显式表示未配置知识源；使用知识时绑定准入来源和准确版本，学习候选关联原始运行证据，发送失败不改写生产结论 |

## 输入与权限边界

输入至少包含目标、验收条件、项目来源引用、文件相对路径、原内容绑定、修改方案、验证引用，以及尝试次数、时间和输出预算。当前公共数据结构见[公共接口](INTERFACE.md)，格式带有版本标识。

运行同时绑定执行实例与调用主体、所选 profile、协议/能力版本及归档实例。恢复必须沿原绑定核对；同一 socket 路径或相同文件名不能证明部署和数据身份没有变化。调用方重试创建运行、提交修订或记录决定时，使用原请求标识与内容绑定，不因丢回执生成重复动作。

首版仅消费明确配置的能力及调用方已有权限。控制组件不发明授权，也不因为知道文件路径就获得修改权限。执行前从真实能力响应核对来源和验证引用；项目未登记或能力不匹配时给出具体原因，不猜测机器配置或扩大服务能力。

第一次实际试点选用待处理的真实任务。历史已完成任务可只读核对，不重新提交；不为了凑演示修改无关代码或要求另建示例项目。

## 失败、未知与后续尝试

- 本地输入或预检失败不冒充远端执行。修正后可以继续，保留原错误。
- 准备未完成时沿原 UUID、kind、profile 和 inputs 调用 `lh_job_prepare` 接续；`PREPARING` 不能仅靠 `lh_job_status` 推进。准备失败修正原因后可用原参数加 `retry_failed=true` 重试。提交丢响应后查询原任务；不得更换 ID、执行器或目标重放结果未知的业务。
- `NOT_FOUND`、CLI 超时、控制进程退出或本地没有成功记录，都不单独证明远端未接受请求；恢复要核对原调用者/子进程、原部署和原请求。
- 原调用退出或原输出管道无法确认时，仍可沿原身份只读查询；不能把安全查询也阻塞在缺失的退出证明之后。
- 已确认业务失败且原执行停止后，可接收修复方案创建新的业务尝试；新旧尝试保持关联。
- 只读调用允许有界重试。超过预算后保存接续点，不无限轮询，不将读取失败变成永久禁止恢复。
- 取消先阻止本控制器继续提交和修复。准备阶段尚无业务可取消时也要保留这一屏障；已提交的任务再通过取消入口并核对退出。任务恰好先完成时保留真实业务结果，不因随后发出取消而改写成取消成功。
- 取消入口不能被等待外部响应的长时间状态锁挡住。取消先到、提交后到时，首次取消的 `NOT_FOUND` 不代表后续提交已被阻止；保留意图，发现原任务接纳后继续申请取消并核对退出。
- 归档失败不改变已经观察到的业务结果。失败或未知任务仍保留状态及可用证据，不伪造成功封存包。
- 归档与运行记录是不同持久化边界；丢响应先核对原写入，不覆盖、清空或重新初始化既有存储。
- 成果读回也会写本地输出目录。目录已发布但回执丢失时保留原目录，按同一版本另选新目录重新读回并核对；不能覆盖原目录、仅凭目录存在认定成功，或重新执行业务。

## 验收与完成范围

首版验收需要一个安装态的真实任务闭环，并覆盖提交丢响应、控制进程重启、取消待退出、失败修复和成果损坏等相关边界。替身测试可以证明本地协调行为，不能代替真实执行适配、安装或端到端消费。

对成功路径，必须能从目标追溯到执行身份、原请求、验证结果、指定成果版本及验收决定。后续审查应确实读取归档中的内容，不能仅查询元数据或保存一个未使用的版本号。

成果内容完整不等于属于本次任务。必须同时核对归档来源、任务及请求、源提交、文件路径、前后内容摘要和固定验证引用。验收只针对已核对的特定候选与目标版本；原候选的接受决定不得自动套用到后续修订。接受时每项必需验收条件都应有依据，证据缺失或冲突不能靠一个无绑定的 `accepted=true` 覆盖。

固定验证可能修改任务副本。首版还要确认验证结束后的源码差异仍对应所审查的单文件候选；若验证改了其他源码或留下无法解释的额外变化，应保留缺口，不能声称该单文件候选已单独通过验证。

未接受、需修复、已取消和结果未知都是需要准确表达的结局；不能统一折算为成功。验收拒绝后的修复仍受原目标和预算约束。

这一闭环可为 Ledger A3 提供 Code Driver 一侧的真实消费证据。A3 还要求独立 Generic Agent 的实际消费；本仓两次运行、两个脚本或知识组件接入不自动补足另一消费者。它也不代表完整生产系统或全部跨仓能力已经验收。

知识服务未配置时明确记录“未使用知识”，不伪造已准入知识包。已配置但不可用时，按该运行预先确定的必需/可选属性处理；可选降级要留下原因。生产经验可以形成有来源的学习候选，未经外部准入不得自动成为有效知识；回流失败单独保留，不将已完成生产改报失败或重复执行。

## 本阶段不实现

多租户、并行生产图、任意 shell 执行、自动生成修复、自动 Git 提交合并、自动部署、通用执行器 Hub、完整知识库、自动生成学习候选以及正式治理决策服务。保留必要的接口边界，后续范围根据真实需求和现有验证推进。


## 新执行的知识前提

已登记采用和当前可执行分别判断。对于计划声明 SELECTED 的知识，提交新执行前须核对原 K 使用回执仍存在、原准确版本仍 ACTIVE 且条件与声明上下文匹配、内容和材料可核对；失效或读取失败时保留原动作与失败，不新增执行或消耗业务额度。不可自动替换成最新知识，输入改变须显式修订。已提交任务的原身份查询、取消和迟到反馈不因旧知识退休而失效。

该检查不承诺与后端执行原子，也不能凭一个旧快照中的 ACTIVE 判断恢复后的当前资格；组合恢复需另行核对恢复点、后续决定和原写入者隔离。

## 明确学习候选的可靠投递

Owner 已批准本阶段接通 P 到 K 的候选回流。调用方明确给出经验、适用条件和允许分享的材料引用；P 保存原任务身份及投递时观察，先发布材料，再登记待审候选。接收回执不能代替审查、版本生效或实际采用。

成功标准：重启、K 提交后丢响应及 P 确认前失败，均沿原请求找回同一材料/候选；不得重复生产、不覆盖原结果。目的库或内容改变拒绝，已确认过的回执后来丢失不自动重建。运行修订或取消后仍可投递原尝试的材料，不能误绑当前尝试。
