# 架构：控制过程与基础能力分工

状态：首版完整闭环设计，与[需求](REQUIREMENTS.md)配套。`0.1.0a6` 已实现运行记录核心、静态 CLI 适配、验收记录和 K 采用/反馈/明确学习候选投递，精确 API 见[公共接口](INTERFACE.md)。原部署的真实 README 候选已完成执行、归档、准确读回和 ACCEPT；后续本地应用与发布单独记录。组合恢复已完成历史只读对账及同机原路径受控启用，范围为原 P 记录/回执接续、K 新采用/反馈和准确材料/成果读取；恢复后的原成果归档 CLI 读写接续、跨机切换及完整生产资格仍待验证。具体恢复和取消窗口见[开发记录](DEVELOPMENT.md)。

## 组成与依赖方向

首版使用 Python 3.12、Linux 和单用户 CLI，核心协调逻辑作为可导入库；CLI 与库共享相同操作语义。选择这个起点是为了复用已有 Local Hand 结果归档能力，不代表未来仅支持这一平台。

| 模块或端口 | 本仓负责的内容 | 外部事实或决定的来源 |
| --- | --- | --- |
| 控制核心 | 目标推进、尝试关联、修复条件、恢复顺序及预算 | 消费明确目标、执行观察和决定，不覆盖来源事实 |
| 运行记录端口 | 持久化本控制器的输入、待发动作、回执、观察及接续点 | 远端执行状态仍由执行后端报告 |
| 执行适配器 | 将已绑定方案转换为准备、提交、查询、取消和证据读取操作 | Local Hand 公共接口及其原任务账本 |
| 成果适配器 | 保存合格候选引用，按精确版本读回并核对 | 现有归档 CLI，经 Ledger 公共库接口保存内容 |
| 验收输入 | 关联来自指定验收者的接受、拒绝或需修复决定 | 首版为本机操作者明确给出的决定，不实现通用治理服务 |
| 可选知识读取端口 | 绑定被选用知识的准确版本、准入来源和适用条件 | 知识与准入组件决定知识状态；控制器不能自授准入 |
| 可选学习候选出口 | 保存带运行证据来源的候选及发送状态 | 接收方只确认收到候选，收到不等于准入为有效知识 |

依赖由控制核心指向端口，再由适配器调用公共接口。Local Hand 和 Ledger 不反向依赖本仓。外部应用通过本仓入口使用协调能力，不访问内部数据库表。

首版采用显式配置的静态适配器。尚未出现实际复用需要的模块先留在仓内，不能为了抽象完整而提前创建 Hub、契约发布服务或更多仓库。

## 目标、运行和尝试

- **目标与验收条件**：固定版本和内容绑定，说明期望结果；修复不得静默降低标准。
- **计划修订**：绑定输入、来源、执行能力、验证方式及预算。改变方案形成新修订，保留历史。
- **运行**：推进同一目标的过程，拥有稳定的本地运行 ID。
- **尝试**：一次具体业务执行，关联计划修订和独立的 Local Hand `operation_id`。对同一尝试恢复查询时复用原任务 ID 与请求。
- **成果引用**：明确 Artifact ID、Version ID 及其来源尝试，不提供隐式“最新成果”选择。
- **验收决定**：绑定目标、候选版本和依据；声明者、时间和原因可追溯，不冒充外部已认证签名。

执行绑定至少保存稳定实例标识、`authority_id`、映射的调用主体、profile、工具 schema 标识及所选来源/验证信息。恢复时核对身份和兼容性；地址可以经确认迁移，但不能因为原路径可连接就静默换实例。归档的 `producer` 在首次使用前与该实例明确绑定并持久化，不能随重启重新生成。

创建运行、提交修订、记录取消意图与验收决定等本地写操作，也需调用方请求 ID 和规范化内容绑定：相同请求重放返回原结果，同 ID 不同内容拒绝。它们与 Local Hand 任务 ID、Ledger 成果 ID 分开管理；本地去重不代替远端去重。

核心分别保存“控制推进到哪里”“执行后端观察到什么”“验证得到什么”“验收者决定什么”。不能用一个成功布尔值覆盖这些不同结论。当前公共状态与操作语义见[公共接口](INTERFACE.md)；这里的职责说明不代替具体接口合同。

## 持久化与副作用

首版由仓内运行记录模块独占一份本地 SQLite 数据库，保存本控制器的协调记录。它不读取或修改 Local Hand、Ledger 的私有表，也不成为远端进程状态的新权威。

该模块是未来运行记录组件的候选接入位置；尚未实现独立的 `infra-runtime-ledger` 服务，也不宣称本仓实现了其完整规划职责。未来替换必须迁移原身份、未决动作和历史记录，不建立两套可各自修改的运行事实。

一次可能有副作用的调用按以下顺序推进：

1. 在本地持久保存精确输入、绑定、原任务身份和待发动作。
2. 调用外部公共入口。
3. 保存回执或失败；没有确定回执时保留未决状态。
4. 恢复时先读取待发动作，查询同一外部任务或原写入结果，再决定是否能继续。

本地数据库和远端操作不构成跨系统事务。进程在任一边界退出，都不能通过本地“未记成功”推出远端“没有执行”。执行适配器的去重、查询与来源绑定是恢复依据。

首版在同一控制存储内串行推进业务，同一运行只允许一个推进写入者，使用进程级互斥和数据库事务；查询不隐式推进业务。竞争、损坏或不支持的存储版本应显式报错，不自动覆盖或新建替代存储。状态目录、证据和凭据保持私有，日志不回显密钥。

执行者占用与短时状态锁分开：串行执行权防止第二个推进者重复下发，状态锁保护意图、回执和取消标记的原子更新。不能持有状态锁或 SQLite 写事务等待外部 CLI 返回、轮询或完成整个业务，否则取消入口无法及时登记意图。下发前在短事务内核对取消并记录“可能已发送”；此后发生取消按在途调用处理，不能保证撤回已经越过该边界的提交。

首次初始化与打开已有存储是不同操作。已有运行的数据库、绑定或待决记录缺失时，不把空目录当成新运行初始化。首版不承诺丢失全部状态、数据库回滚或任意断电后的自动恢复；识别到不一致时先核对保留记录和外部任务，不能将旧快照中的“未提交”当作当前事实。

进程锁释放不代表它启动的 CLI 子进程已经退出。适配器要保留调用身份、可核对的子进程生命周期与双流完成情况；CLI 超时或被杀也不等于远端任务停止。恢复先约束旧调用仍可能产生的副作用，再依据公共接口接续；不能只靠取得新锁就重新发送。

旧调用的退出或原匿名管道 EOF 无法确认时，限制的是有重复副作用风险的下发；原身份下的只读查询仍可有界进行，用来补足判断。不能要求先证明旧调用全部结束，才允许查询它是否已完成；原始采集缺口仍如实保留。

## Local Hand 适配

首版优先通过已安装的公共 CLI 和其 Unix socket 接入，不要求为本仓更换现有管理服务或新增 MCP 工具。能力来自实际部署，源码中有某功能不等于当前服务已开放。

| 公共工具 | 本仓使用方式 |
| --- | --- |
| `lh_capabilities` | 核对已开放任务类型、来源和验证引用 |
| `lh_workspace_read` | 读取获准来源文件及绑定信息，核对原内容 |
| `lh_job_prepare` | 保存小写 UUID v4 后准备；`PREPARING` 沿原参数调用此入口轮询，`FAILED` 修正原因后用原参数加 `retry_failed=true` |
| `lh_job_submit` | 提交原准备结果中的请求，保存原请求摘要 |
| `lh_job_status` | 查询原任务，区分执行、业务及证据状态 |
| `lh_job_cancel` | 针对原任务及请求摘要申请取消，随后继续核对退出 |
| `lh_evidence_manifest`、`lh_evidence_read_chunk` | 完整读取清单与分块，核对大小、摘要和封存绑定 |

`workspace.edit` 在独立任务副本中修改单文件并运行固定验证，返回补丁、前后内容及验证输出。控制组件不将其解释为原工作区已改变；本阶段不调用本地应用入口。

当前常驻入口不提供通用的 `lh_job_reconcile`。控制进程的恢复是读取本地接续记录并查询原任务，不假定能够通过未开放工具修复远端任意状态。需要后端维护时保留具体缺口，不靠重新提交绕过。

不同中断点按实际阶段恢复：

| 中断点或观察 | 接续动作与边界 |
| --- | --- |
| 准备未完成或准备回执丢失 | 原参数调用 `lh_job_prepare`；状态查询可能返回忙或未找到，不能替代准备轮询 |
| 已收到 `READY`，尚未记录提交意图 | 持久保存返回的完整 request 和摘要；提交前再次检查取消、权限和预算 |
| 准备请求过期、部署启动变化或已证实的接纳前失败 | 旧调用不能继续落账，且原服务依其未接纳检查允许重新准备时，沿原 ID 和原 inputs 接续；新 `READY` 请求另存为准备修订，不覆盖已发送的原请求历史，不复用旧修订下发 |
| 提交意图已存、回执未知 | 先查询原任务；仅在原调用状态和后端去重语义足以保证安全时，重发同一有效请求，不能从一次 `NOT_FOUND` 推断从未下发 |
| 业务已完成、归档未记成功 | 保留业务结果，按原归档身份核对或恢复，不重新执行 |

准备状态不等于业务状态。改变修复内容时形成新的业务尝试；对原准备的重试不得夹带新的 inputs。`READY` 请求包含绑定与有效期，应原样使用，不能重新拼接一个看起来等价的请求。

## 成果归档和真正使用

首版复用 `local-hand-archive archive / read / resume` 作为成果适配器，而非重写已存在的归档协议。该工具在内部使用 Ledger 公共接口；本仓不直接写它管理的 `ledger.sqlite`。

归档输入必须来自真实认证的状态响应和对应证据，可信摘要在接收时保留。对任意文件自行算一个摘要不能证明其来自指定执行器。现有入口要求 `TERMINAL / EXITED / SUCCEEDED / SEALED` 和唯一可信 seal 引用；失败任务的观察和现有证据另行保留。

归档返回的 Artifact/Version 引用写入运行记录。后续审查通过 `read` 读回精确版本，使用读回的补丁、前后内容和验证报告判断是否满足目标，并记录使用了哪个版本、得到什么结论。读取输出使用新目录，不覆盖既有成果。

归档工具验证包内自洽性，本控制器还须将返回的 `source` 与原运行绑定逐项比较：producer、operation ID、request digest、seal 身份/摘要、workspace 的 source ref/commit、relative path、before/after 摘要和 validation ref。一个完整但来自其他任务或其他计划的合法包也必须拒绝。`workspace.edit` 候选必须存在对应 workspace 描述，不能把成功的主机检查包当作修改成果。

Local Hand 会记录验证前的 `workspace.patch`、验证后的 `workspace-final.patch` 和最终 `git_status`。归档器检查目标文件未被验证改写，不代替控制器检查其他源码变化。首版候选要求前后补丁一致，且最终状态没有额外已跟踪源码修改；未跟踪生成物依固定验证的明确允许范围核对，无法解释的差异阻止接受。相关文件均应来自已验证 manifest 中的成员，缺失不当作通过。

`read` 输出是归档目录之外的新目录，包含 zip、manifest、seal、status 与 source 五份文件。核心通过验证后的成员读取候选内容，不直接执行包内代码或无约束解压。读回收据记录实际审查字节的摘要和准确版本；若展示/使用文件之后发生变化，应重新核对，不让路径名称代替被审查内容。

`read` 不修改 Ledger，但会创建输出目录；它不是可无条件重试同一路径的纯查询。调用前持久记录准确版本与本次输出位置。若输出已发布、回执尚未保存就中断，不以“目录存在”判定读回成功，也不删除原目录重试。先保留原尝试；确认旧调用结束后，在读取与磁盘预算内选择另一个不存在的输出目录，重新读取同一版本，取得并核对完整响应后记录新的读回收据。旧输出和失败保留，业务与归档写入均不重做。

`archive` 的创建身份与追加版本是分开的 Ledger 事务；非零退出不能推断全部回滚。丢响应使用原 producer 和 operation ID 进行 `resume`，保留整个归档目录，不重新生成一套身份。业务已完成时归档重试不得触发业务重跑。

首次归档前保留可信状态原始字节、摘要和完整证据。若中断发生在归档器建立恢复材料之前，`resume` 可能无从恢复；先确认原调用结束并按该入口的去重/冲突规则核对，再决定能否用原身份和原字节重新调用 `archive`。不得因一次未找到就清空存储或更换 producer；已有保留材料缺失与从未进入归档要分别处理。

默认存储为满足现有归档工具要求的本地持久文件系统；不能把归档工作目录放到 NAS 或共享目录。Ledger 的快照恢复属于独立能力，本首版不重做已完成的 A2 现场任务。

## 修复、取消与资源

首版修复方案由调用方提供。只有原执行已确认停止、结果已明确、原目标和预算允许时，才形成新的业务尝试；失败或验收拒绝不会覆盖前一尝试。 对仅写任务独立副本的 workspace.edit，已核实的维护退出证明可独立保存，保留原 UNKNOWN 并允许其他明确获准运行继续；它不改报远端状态、不退还原业务额度，也不重新开放旧任务。证明与原请求、部署及全部写入者退出绑定，具体条件见[公共接口](INTERFACE.md#调用与恢复语义)。

修复产生一份新计划修订及候选，不继承旧候选的接受决定。前一尝试的结果、剩余证据采集和归档是否需要继续分别记录；不为修复而覆盖前一候选或清理未决材料。

普通本地校验失败与只读连接错误可修正或有界重试。业务结果未知时进入待核对状态；之后出现可验证新信息可继续，不把一次失败永久锁死。取消请求持久化后继续查询；时间预算耗尽也不能把仍在运行的任务记为已经退出。

取消意图在与提交/修复推进相同的短时状态锁和事务边界内形成屏障，入口不等待执行者释放整个业务期间的占用。准备中取消先禁止后续提交或自动重新准备，当前入口不保证能中止准备进程；允许它结束并保留资源事实。提交已经可能发出时，按原 ID 和 request digest 请求取消并查询退出。业务与取消竞速时，分别记录用户停止推进的意图和后端真实结果；先完成的成功不改写为取消，原失败也不被取消回执覆盖。

当前服务不会替尚未接纳的任务预约一次未来取消：原任务尚处 IDLE 时取消可返回 `NOT_FOUND`，准备未就绪时可返回 `RESOURCE_BUSY`。若提交仍在途，这些返回均不能关闭本地取消意图。保持禁止新下发，在独立预算内查询同一任务；后续发现已接纳且未退出时，核对摘要并再次请求取消。收到取消回执后继续查询退出；鉴权拒绝、身份冲突或无退出证明仍是待处理事实，不能靠换身份、重提业务或假报取消成功消除。

尝试次数、总时限、单次调用时限、读取大小和磁盘预算在首次副作用前明确。预算耗尽停止新下发并保留查询与取消所需记录；失败重试不能绕开预算。具体默认值随真实适配限额确定，不用无限值掩盖未设计资源约束。

业务尝试额度在提交意图持久化时预留；确认未下发或被拒绝且没有执行后才能释放，结果未知时继续占用。准备轮询和只读重试消耗各自请求/时间预算，不冒充新的业务尝试；重启不重置已消耗预算。取消与只读核对保留独立的有界预算，耗尽后保存接续点，不把无退出证明的任务标为终止。

## 验收与未来扩展

首版用明确的本机操作者输入承载验收决定；CLI、测试输出和控制核心不能自行授予其额外权限。后续正式授权、证据准入和生产验收服务通过各自端口接入，分别拥有其决策职责。

决定至少关联目标版本、计划/尝试、准确成果版本、已验证读回收据和各必需条件的依据。接受前检查引用与内容仍相符；旧候选的迟到决定只属于旧候选，不能改变当前候选状态。重复同一决定返回原记录，更正另增引用原决定的记录，不覆盖历史或追溯改写已发生动作。

以下为知识与学习边界。知识读取、准确版本采用及使用反馈已有 K 公共接口适配；学习候选出口已接通明确配置的 K，未投递与已接收分别记录：

| 方向 | 最小输入与结果约束 | 未配置或失败时 |
| --- | --- | --- |
| 知识读取 | 查询包含任务上下文与适用条件；结果包含知识 ID/准确版本、内容绑定、准入来源及适用范围。只有有可核对准入依据的条目能作为已准入知识使用 | 分开记录未配置、无匹配和查询失败；可选能力可以显式降级，目标要求必需知识时阻止依赖它的新执行 |
| 学习候选回流 | 候选有独立 ID，关联目标/运行/尝试、输入与环境引用、失败及修复经过、验证结果和证据/成果版本；包含有待验证的解释，不自称有效知识 | 本地保留候选与待发送状态；有接收方且分享范围获准才发送，重试同一 ID，接收回执与准入决定分开 |

读取的知识版本在计划中固定；外部知识更新不自动改变已开始任务的授权、要求或输入。无接收方时只保留本地候选，不能假报已发送；回流失败不回滚已完成生产，也不触发业务重跑。候选形成与发送状态可单独接续，敏感原文按任务分享范围处理。

可替换执行器和本地/云端部署留待后续真实适配。不引入旧整体原型作为运行宿主，不以端口存在宣称知识准入、学习能力或跨实现可替换性已验收。

## K 调用的持久化

每个尝试的 K 使用 ID 由 P 存储身份、运行 ID、尝试 ID 和操作确定，目标是让调用者重启后沿原记录核对。`knowledge_calls` 保存原请求、目标 K 身份、修订、pending/committed 状态和回执；请求意图、确认与 P 事件各自原子提交。调用 K 时不持有 P 写事务，但使用原执行租约阻止另一推进者同时提交业务。取消仍可记录；在知识登记与取消竞争时，已发生的采用保留，但取消屏障阻止业务提交。

采用前核对 K 的公开锚点回执、ACTIVE 状态、内容摘要、审查引用、适用条件与原材料可读性；K 在自己的事务中再次检查新采用条件。选用信息固定在原计划，原使用回执只证明历史登记，新提交还须重新核对当前版本、条件和材料。反馈保存所指定旧修订的实际观察快照，迟到响应也只确认原调用。跨库结果未知时先查询 K 原回执，再恢复原幂等请求；不以知识反馈重放生产。


## 执行时知识检查

P `perform` 在执行器预检之后经配置的 K 公共接口读取原使用和准确版本；当前观察及 P 本地取消、修订、请求、预算检查均通过后才登记 dispatch。读取期间不持有 P 写事务，当前观察在同一提交事务中保存到动作；检查对象与原尝试、计划和原使用绑定，不能用另一动作或旧缓存替代。K 负责知识状态与材料关系，P 消费该状态决定能否发起新执行；具体接口及并发窗口见[知识接入](KNOWLEDGE.md)。

检查后的跨组件竞态仍按在途任务合同处理；本能力不提供跨库原子授权或恢复副本的新鲜性证明。产品组装流程负责选择兼容实例和恢复点，协调停止原写入及组合验收；各组件不因这条检查承担整套产品部署管理。

## 学习候选投递的两次提交

`learning.py` 复用知识适配器的 K 实例/锚点核对，通过公共 `publish_material`、`propose` 工作。首次投递在 P 原候选 JSON 中保存 `delivery_record`：来源摘要、明确提案、目的 K 身份/作用域、两个准确请求及各自回执。请求 ID 和材料/提案逻辑 ID 由 P 存储身份、本地候选 ID 与操作确定；调用前预留有界回执空间。无新增数据库表。

材料是投递登记时冻结的原尝试观察、候选解释和引用，不是所有证据原件的副本。指定的成果版本须匹配 P 已记录的成果候选；补充 K 材料由 K 按公共合同核对。材料与提案各自完成 K 提交后，再将准确回执写入 P 事件/回执；这不是跨库原子事务。传输不持有 P 数据库事务，持有原执行租约，取消仍可独立记录。

恢复逐步查询两个原 K 回执；未找到且 P 尚无确认时，使用同一请求调用 K 的幂等接续。P 已确认的回执缺失则拒绝重建。`delivery=RECEIVED` 仅说明候选登记成功；`admission=NOT_REQUESTED` 表示此适配器没有请求准入，不代表 K 当前仍待审。当前审查/知识状态须从 K 另行查询。旧候选创建回执保持历史，`get_candidate` 返回当前投递记录。

请求作用域在 `0.1.0a6` 统一支持 1–256 个 ASCII 字符，独立于稳定对象 ID 和知识条件描述的校验。采用、反馈和学习投递共享该规则，容量预留仍按实际 scope 和完整回执计算；配套 K 为 `0.1.0a3`，旧记录无需迁移。
